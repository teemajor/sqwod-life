## Step 3
- **No real job data yet: the build sandbox could not reach any source.** The network policy of this cloud session refused every job host: rest.arbeitsagentur.de, api.adzuna.com, www.dssv.de, insider.fitt.co and all 199 brand sites (201 hosts, `ENOTFOUND` through the proxy). So the brief's acceptance check "a real `--dry` run against BA finds ≥ 20 roles" could not be run here, and `site/src/data/jobs.json` ships empty. Nothing was invented. The page shows an honest empty state, the Tools card for Jobs stays "Coming" and flips to Live by itself after the first run with roles (`jobsLive()` in `site/src/lib/jobs.ts`). **To get real data:** merge, then run **Actions → Jobs → Run workflow** (task `scrape`) on GitHub, whose runners have open internet.
- **Unverified parsers.** The DSSV board (`https://www.dssv.de/jobboerse/`) and Fitt Insider jobs (`https://insider.fitt.co/jobs/`) URLs could not be opened from here. Both are read by a generic reader (JobPosting JSON-LD on the page, else job links and their detail pages). Check their counts in `automation/jobs/last-run.json` after the first run and fix the URL in `automation/jobs-sources.mjs` if a source returns 0.
- **Careers-page discovery has not run** for the same reason, so no brand has a `careersUrl` yet and the list of brands without a careers page is not known. It fills in on the first real run (a site that cannot be reached is retried next week, not marked as "no careers page").
- **JobPosting JSON-LD and the Indexing API are built but switched off** (`JOBS_JSONLD_ON_LIST = false` in `site/src/config/seo.mjs`). I disagree with putting them on `/jobs/`: Google's job-posting guidelines say to mark up the page for one job and not pages that list jobs, and the Indexing API only accepts single job-posting pages. On a young domain with no indexed pages, a structured-data manual action is a real risk. Flip the flag to `true` to emit the markup on every row and ping the Indexing API after each run. With test data both were checked locally: 12 of 12 postings had every required field (title, description, datePosted, validThrough, hiringOrganization, jobLocation or TELECOMMUTE, baseSalary with unitText). The better route is one page per job; that is a later step.
- **On-brand gate.** `isOnBrand()` uses word boundaries, so German compound titles ("Fitnesstrainer", "Studioleiter") failed it. `keepJob()` in `jobs.mjs` keeps `isOnBrand()` and adds a compound check (fitness, trainer, studio, yoga, pilates, physio, sport …) that still respects the OFFTOPIC block. Roles from brand career pages count as on-brand by the brand list itself (a "Software Engineer" at a fitness brand is in scope); "Reinigung" and cleaning roles are always dropped.
- **Adzuna pay:** Adzuna estimates pay when an ad has none (`salary_is_predicted: 1`). Those estimates are not used; only pay the ad lists counts.
- **"5 jobs this week" in the Daily is a section, not an item.** Daily items are fact-checked stories with a source each (`verifyIssue`, `sourceId`, pillar). A list of jobs would fail those checks or bypass them. So on Fridays with ≥ 3 new roles, `cascade.mjs` writes a separate `jobsWeek` block that renders after Money movement on the page and in the email. It never replaces a story, so the item cap stays as it is.
- **Jobs alert email and Resend.** Resend broadcasts go to a segment and cannot filter by contact property. So the Worker puts jobs-alert sign-ups into a jobs segment per language, and **only** that segment: the page promises one email a week, so they do not join the Daily. The alert is sent under a new Resend topic, **"Sqwod Jobs"** (opt-in by default). Its unsubscribe link ends only the jobs alert, never a Daily subscription. In Resend I created the `jobs_alert` property (string, fallback `false`), the topic "Sqwod Jobs" and the segment **"Jobs alert (EN)"**. **The German segment could not be created: the Resend plan allows 3 segments.** Until a fourth is available (plan upgrade, or remove an unused one), German sign-ups get the property but no Friday email, and `jobs-alert.mjs` logs "no RESEND_SEGMENT_JOBS_DE configured". Once it exists, put its id in `infrastructure/subscribe/wrangler.toml` and in the GitHub variable `RESEND_SEGMENT_JOBS_DE`. Also set the GitHub variables `RESEND_SEGMENT_JOBS_EN` = `fb69d0c4-d7e3-459f-848d-7680b351e5d3` and `JOBS_FROM` (e.g. `Sqwod Jobs <daily@sqwod.life>`).
- **Email previews** in `automation/jobs/preview-{en,de}.html` are from the empty data file, so they show the layout with no rows. Re-run `node automation/jobs-alert.mjs --dry` after the first scrape.
- **Schedule.** GitHub cron has no time zone setting (no `CRON_TZ`), so `jobs.yml` uses two UTC slots per job and a once-a-day guard (same idea as `digest.yml`).
- **Jobs page `noindex`** while it has fewer than 10 open roles, like the Deal Tracker guard.
- **Review follow-ups left as they are** (minor): the Claude job summaries are written in neutral German (no "du"), because they describe a posting rather than address the reader. When `JOBS_JSONLD_ON_LIST` is on, `validThrough` is the posting date + 30 days, as the brief specifies, not a date from the ad. A manual scrape earlier on a Thursday makes that evening's scheduled run skip. Deploy fires on every completed Jobs run, including runs with no changes. Redirects are followed without re-checking robots.txt on the new host. Pay will mostly come from Adzuna, JSON-LD `baseSalary`, Lever and Ashby: BA search results carry no pay, and free-text descriptions are not parsed for pay, to avoid false figures.
